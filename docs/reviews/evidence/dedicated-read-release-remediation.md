**Actual cuts and interfaces.** In [game_reads.rs](/home/orangepi/Workspace/brews-bingo/backend/src/worker_runtime/game_reads.rs:539), `GameObject::read_release` flushes storage, obtains fresh Accounts authority for account reads, then synchronously calls `GameService::release_read`. Its successful path has no subsequent owner await. [release_read](/home/orangepi/Workspace/brews-bingo/backend/src/db/game/reads.rs:504) reads the current Game projection in `transactionSync`, compares identity/assignment, intersects deadlines and compares encoded payloads. For participant reads, that final local transaction is the defensible Game authority/content linearization point **L**: Recovery/DELETE/rename/Exit committed before L is observed and causes rejection or a changed projection comparison; a mutation committed after L overlaps the pending read and can follow it in ordinary linearizable ordering.

The edge [dispatch](/home/orangepi/Workspace/brews-bingo/backend/src/worker_runtime/game_reads.rs:308) already performs two releases, with account authorization before each. After the last `/read-release` await it checks challenge, full-request digest, timestamps, rejection and the original/intersected deadline, then serializes the captured projection at line 414. These checks authenticate the cut, not remote state at receipt. Known absolute expiry is locally observable and remains fenced; subsequent epoch, grant or content changes are not.

The edge owns an `Env`, request and reply values, not either owner's `State`. [game_peers::call](/home/orangepi/Workspace/brews-bingo/backend/src/worker_runtime/game_peers.rs:198) obtains a DO stub, awaits fetch and awaits bounded body collection. [OwnerDatabase](/home/orangepi/Workspace/brews-bingo/backend/src/worker_runtime/database.rs:32) synchronously reads only the `Storage` supplied by its own DO. Game can therefore synchronously recut **Game** after its final await; it cannot synchronously read **Accounts**. Accounts can synchronously recut Accounts; it cannot read Game. The edge can synchronously observe neither. There is no existing pending-read invalidation subscription, shared authoritative guard or transaction spanning these owners and edge delivery.

There is also an earlier Accounts return gap: `operator_peers::authorize` accepts a nonce-bound proof after its RPC; Game's local `authorize` checks that proof's role/expiry, not current Accounts SQL. Accounts freshly derives it after its own scheduling/storage awaits (`operator_peers.rs:576`). A revocation can commit after that Accounts cut but before Game consumes the proof. Thus the final Game transaction is not automatically a single atomic Accounts+Game linearization point. Any contract resolution must explicitly cover this gap as well as Game→edge delivery.

**Why another local repair does not close this contract.** Consider two executions delivering identical genuine ACKs before the same deadline: one has no subsequent mutation, the other commits a mutation remotely after the cut. At final receipt the edge has identical bytes, bindings and local time observations, and no synchronous state access to distinguish them. Another Game or Accounts RPC merely moves that indistinguishable final return. Refetching payloads, returning the public Response directly from Game, RPC instead of fetch, revision tags, revocation notifications without commit/delivery ordering, or a tighter positive TTL leave a later delivery gap. Owner serialization/output gates do not fence mutations after the owner returns, or independent Accounts commits. Unconditionally withholding otherwise valid reads would sacrifice the authorized read functionality. No actual-last-return test can both serve the unchanged valid execution and reject all these schedules using the existing information alone.

**Decision requiring user approval.** Either explicitly permit already-authorized in-flight responses when a competing mutation commits after the specified authoritative cut(s), defining Game snapshot timing and Accounts-proof timing separately and retaining receiving-time expiry checks; or retain receipt-time invalidation and authorize coordination that orders relevant mutation commits against pending read delivery. The latter needs an explicit authority owner, delivery/acknowledgement boundary, revocation ordering and crash/timeout/recovery policy across Accounts, Game and the recipient. A lease, mutation lock, account guard or pending-read protocol is additional policy/coordination, not an approved implementation detail. This report approves none. A Game-only guard would not solve independent Accounts revocation. Merely accepting ordinary Game linearization also would not establish atomic joint Accounts/Game authorization.

Preserve the five failing tests and old-invocation control unchanged while that decision is pending. No repair protocol or passing last-return test exists here within the current scope; changing their expectations requires explicit contract approval, not test weakening under the existing contract. Passive reads, no new grants and no additional History retention remain mandatory either way.
