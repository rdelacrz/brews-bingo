## Concrete final-return proof

Edge dispatch performs two release passes (`backend/src/worker_runtime/game_reads.rs:308-383`). After the final await it validates challenge, full digest and times, caps the deadline, handles rejection, then encodes the previously captured projection into HTTP 200 (`:385-421`). The RPC itself awaits both owner fetch and body collection (`backend/src/worker_runtime/game_peers.rs:233-245`). The Game final cut reauthorizes Accounts where applicable and recuts local content (`game_reads.rs:630-680`); ordinary release uses a local SQL transaction and compares identity, assignment, cap and encoded projection (`backend/src/db/game/reads.rs:510-562`). Creation-pending G4 also recuts remote Directory state (`game_reads.rs:491-508`; `command_lookup.rs:151-192`).

Let L be the last authoritative owner cut, M a competing committed mutation, E the edge's success construction and B its body emission. The retained schedule is L < M < E; no expiry is needed. A no-mutation execution can supply exactly the same legitimate ACK, digest, nonce and local time as the mutation execution. Without an authoritative synchronous remote-state observation or a durable ordering protocol, edge observations are identical at E, so serving the valid execution also serves the revoked execution. A finite extra RPC replaces L with L2; schedule M after L2. A shorter TTL still admits a mutation before expiry. Per-invocation binding prevents substitution from another invocation, not changes after this invocation's legitimate cut.

There is a separate Accounts→Game gap. `operator_peers::authorize` returns a remote proof and locally checks expiry (`backend/src/worker_runtime/operator_peers.rs:262-298`); Game SQL cannot read Accounts SQL. `OwnerDatabase` has only its supplied owner's Storage (`database.rs:8-13,31-36,67-90`). Thus even a Game-local transaction does not establish simultaneous current Accounts and Game state. A Game-only read lock leaves credential-epoch/revocation mutations outside its fence.

Direct/opaque forwarding changes no ordering: owner constructs a response at L; transport can hold it; M commits; the edge subsequently forwards it. Streaming gives the analogous schedule: owner enqueues a protected chunk at L; the chunk is delayed between owner and edge; M commits; the edge later emits it. Moving the checked boundary to owner enqueue would change the requirement. These are counterexample schedules derived from inspected interfaces, not newly executed probes.

## SDK and exact boundary

Pinned `worker = 0.8.7` is at `backend/Cargo.toml:34`. In the installed `/home/orangepi/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/worker-0.8.7/src/http/response.rs:17-51`, conversion fixes status/headers and wraps the Rust body in a ReadableStream. `src/http/body.rs:150-170` polls the body and copies frames to JS byte arrays. Installed `worker-macros-0.8.7/src/event.rs:106-126` awaits the handler then converts its response. The SDK supports a custom body poll and local synchronous flag/deadline check, but supplies no synchronous shared Accounts/Game grant view and no browser-delivery acknowledgement. `worker-0.8.7/src/context.rs:26-46` wait_until extends work, not a response/mutation transaction.

This distinction is corroborated by primary provider documentation: [Response](https://developers.cloudflare.com/workers/runtime-apis/response/) supports stream bodies; [Streams](https://developers.cloudflare.com/workers/runtime-apis/streams/) describes emitting the body after status/headers; [Durable Object gates](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/) hold output until storage writes complete. Inference: none of these mechanisms establishes current remote authority when a downstream recipient receives delayed bytes. Output gates persist prior writes, not locks on later independent commits.

Three boundaries must not be conflated:

1. Handler success/headers: the retained probe requires 401 or 503 and no receipt, not 200 with a subsequently aborted body.
2. Application-controlled edge body handoff: a practicable stronger server target could forbid every new protected chunk after a conflicting commit, while explicitly allowing previously handed-off bytes to arrive later. Status cancellation after headers requires an approved transport-error contract; partial JSON bytes can themselves contain protected data.
3. Physical network/browser receipt/render: bytes already sent cannot be recalled. Delaying/reordering packets or pausing a browser produces later receipt after revocation. A browser ACK does not erase knowledge and can be withheld indefinitely. A policy promising no later physical receipt is not realizable by these APIs.

An isolate-local cache/flag is useful only as the receiving half of a proven ordered protocol; it cannot be authoritative across different isolates, hosts, reconstruction or restarts. A single local WebUI server with a shared synchronous store could atomically check and enqueue locally, but that changes deployment architecture. This workspace has no frontend crate (`Cargo.toml:3-4`) and is API Worker based (`worker_runtime/mod.rs:53-83`); a local dev UI proxy neither repairs deployed distributed authority nor authorizes frontend implementation. A public subscription allowing already-authorized in-flight outputs is a policy option only with explicit approval; DO-036's existing WSS in-flight allowance (`durable-object-design.md:415`) does not waive the dedicated HTTP contract.

## Smallest coherent strict protocol to design, if authorized

For application edge handoff semantics, the minimum is durable pending-response coordination, not one release endpoint:

- Register each response attempt before selecting protected data; bind exact actor/session/epoch, Game, selection/projection digest, original cap and attempt incarnation. Cover Accounts invalidation, Game identity/final-grant/content changes, and Directory creation facts when those are returned. New durable registration writes also extend today's passive-read write contract.
- Each relevant owner acquires/records a conflicting mutation intent, rejects new registrations in that scope, and resolves existing attempts. Use a fixed acquisition order and narrow scopes; never await a peer inside a SQL transaction. Game content mutators include changes to the selected payload, not only Recovery/Exit.
- The actual edge emitter must be reachable independently while its owner reply is held. Cancellation and the last local pre-header/body check must serialize in that emitter. A mutation commits only after every affected attempt is proven cancelled before emission or proven handed off before commit. A coordinator-issued permit alone is not evidence of later handoff.
- Persist exact completed/cancelled acknowledgements and retry intents; retain uncertainty across owner/edge reconstruction. ACKs must refer to the exact attempt/incarnation and cannot clear successors. Do not persist protected bytes or secrets in guard/audit records.
- A lost ACK or stalled edge cannot simply expire a lock and permit commit while the old edge may resume and emit. A lease needs a proved self-fencing emitter deadline, trustworthy clock/skew assumptions, and fail-closed checks on every later emission. Durable time floors in independent owners do not automatically supply shared edge clocks. Otherwise preserve the fence and report unavailable/pending instead of false success. This safety/availability tradeoff needs an explicit policy.
- Preserve absolute session/History deadlines and terminal expiry: no lease may renew access/retention or postpone logical expiry. Cancellation on expiry must precede any further protected emission; later physical receipt of already handed-off data is outside the enforceable boundary.

This is a proposed architecture and proof obligation, not an SDK-validated implementation. There is no existing reverse edge-control protocol or validated crash/lease fencing mechanism. Mutation success may now wait or become pending/unavailable, and that is observable contract change. Purely holding Recovery until the held read returns creates a circular wait in the unchanged probe (the hook awaits Recovery before releasing the read). A correct cancellation design must instead let Recovery complete after positively cancelling that still-pending read, and the resumed read must deny. Do not call a timeout or a 200+stream-error a passing version of that assertion.

The strict protocol must be proved for all mutation entry points, including CLI/internal recovery/alarm paths, not only public APIs. Accounts disable/reset/remove and all-session Exit are wider than one player read guard. Clocks, bounded retries, caps, typed states/errors, schema validation and durable alarms must follow AGENTS and `docs/rust-best-practices.md`; no proof here establishes them.

## Alternative only with explicit policy approval

The smallest implementation option preserving immediate mutations is explicit earlier-cut semantics: define participant snapshot authority/content at the Game transaction; separately define Accounts proof time and Directory cut, or introduce an account guard to provide joint authority if that stronger property is selected. Keep original receiving-time expiry checks, denial fences and fresh request binding. Allow a mutation committed after those named cuts to overtake an already-authorized read. This is weaker than the retained receiving-cut requirement and would intentionally permit its held 200. It cannot be sold as a repair under the present contract. Keep historical probes unchanged; record them as evidence against the superseded contract and add separate acceptance tests only after explicit policy revision. Do not hide them with excludes, expected-failure conversion or green release labels.

## One minimum clarification for the parent

Suggested wording: “RUNTIME-FINAL-01 requires a response policy choice. Should we (A) retain strict invalidation through application-controlled edge response/body handoff and authorize coordination that may delay a conflicting mutation or return an explicitly defined pending/unavailable result until affected responses are cancelled or handed off, including a fail-closed crash/timeout policy; or (B) preserve immediate mutation behavior and explicitly allow responses already authorized at named Accounts/Game/Directory cuts to finish after a competing commit? Already-sent bytes may arrive later in either case; the server cannot guarantee physical browser-delivery invalidation.”

Recommend A if the existing strict requirement is retained. Ask for policy selection first; do not invent concrete maximum waits, new statuses or orphan lease expiry as approved values. A user selection of A then requires a concrete bounded deadline/status/crash contract before implementation, which can be proposed together rather than a long chain of questions. If the user insists on both unchanged immediate mutations and invalidating all distributed pending responses with no coordination delay, state that no satisfying implementation has been established; do not downgrade to B silently.
