# Local CI and controlled promotion

This slice implements local deployment tooling and GitHub workflow definitions. It has not deployed a Worker, provisioned an account/namespace/secret, run the remote staging game, or verified GitHub environment settings. The seven remaining external gates in `docs/plans/PENDING.md` remain OPEN after the separately approved [Argon2 performance-gate removal](../plans/argon2-default-policy.md) and the retained RUNTIME-FINAL-01 receiving-cut assertion remains historical failure under the superseded policy. Nothing here grants production readiness. Publication and real provider actions require separate authorization.

`validation.yml` runs on PRs and pushes to main with read-only repository permissions and no secrets. It runs Python unit tests and the existing full local release runner sequentially. Exit 1 or 2 from a mandatory gate fails the job; the original receiving-cut probe is retained separately as historical failure. Both validation and release freeze install the Ubuntu OS package `mold`, require x86_64, and compile/run a tiny `cc -fuse-ld=mold` link check before installing native cargo tools or running tests. This satisfies `.cargo/config.toml`; local ARM testing does not validate the hosted x86 linker. No local OS installation was performed. It installs Rust 1.99.0, worker-build 0.8.7, cargo-nextest 0.9.140, Node 22.16.0 and Python 3.14.0; npm uses the repository lock and Wrangler 4.147.0. The worker-build version comes from backend/README.md and nextest matches the installed baseline tool (upstream tag independently checked). Third-party GitHub actions use full upstream commit hashes, verified using public `git ls-remote` tag reads on 2026-10-14.

`release.yml` (`manualprodapproval`) only accepts workflow_dispatch on main with the explicitly requested 40-character commit equal to the event's main SHA. A fresh checkout builds/tests once through the local runner, including the native CLI, and freezes source hashes, exact gate/probe inputs, the four deployment files, the original Rust Wasm artifact and the tested native CLI. The canonical manifest records locked tools, commit, code hash and safe local gate evidence. It transfers only an allowlisted archive; no source checkout, dependencies, logs, credential files or harness account data enter that archive. Manifest and archive digests travel as same-run job outputs; upload-artifact v4's immutable same-run artifact and the trusted workflow are the trust boundary, not a standalone signature from an arbitrary archive author. Each destination verifies the archive digest, allowlisted names/size/link constraints, manifest digest, exact source hashes and asset hashes. There is no arbitrary run/artifact input and no production rebuild.

The entire release run holds `brews-staging-production-promotion` concurrency, including staging deployment/game/identity checks and the production approval wait. `cancel-in-progress` is false. Administrators must forbid independent Cloudflare Workers Builds, dashboard/CLI uploads, other workflows and other writers for these Worker names. GitHub concurrency alone cannot serialize external writers. The reviewed manifest attests that external automatic deployment is disabled; identity readback also detects changes during and after testing and after the production approval wait. Cancellation/timeout can leave a partially completed release; do not assume it restored the previous version.

## Isolation and provider prerequisites

The existing top-level local Wrangler config and historical migrations (`accounts`, `directory`, `games`) are preserved. Staging/production each repeat all three non-inherited DO bindings, CF_VERSION_METADATA and APP_ORIGIN, have distinct names and reserved `.invalid` origins, and disable workers.dev, preview URLs and routes. They are intentionally unusable placeholders, not provisioning instructions. Never directly deploy backend/wrangler.toml. The tool generates a standalone config with absolute paths to verified frozen assets, no custom build, no bundle transformation, explicit ESModule/Wasm rules, the existing compatibility date/flags and unchanged migration ledger. No staging binding points at the production script.

Before ordinary promotion can run, separately authorized external setup must create each existing Worker, its SQLite classes and namespaces through the exact legacy migration ledger, configure the intended HTTPS host routing, provision separate rate and management secrets, disable previews/workers.dev, and disable parallel autodeployment. First class provision, deletion, rename, transfer, storage conversion and migration modernization are forbidden in ordinary promotion. The tool separately checks existing migration metadata and both the old active version bindings and live bindings before upload; missing state fails closed. It does not repair missing state or upload secrets.

Actual publication uses `wrangler versions upload` followed by `wrangler versions deploy VERSION@100% --yes`, rather than the trigger-changing regular deploy operation. This preserves externally managed routes/domains/settings. The local dry-run uses `wrangler deploy --dry-run --no-bundle` to validate packaging without provider writes. New code preserves APP_ORIGIN and required existing secret bindings; `--keep-vars` preserves externally provisioned vars. Before `versions deploy VERSION@100%`, the exact uploaded version GET must expose all required `resources.bindings`, `resources.script_runtime` migration/compatibility settings, and top-level `version.annotations["workers/tag"]`/`["workers/message"]` matching the commit/code digest. These annotations follow pinned Wrangler 4.147.0’s real GET consumer; upload metadata is not treated as a GET schema. Settings annotations are never an authority. Post-promotion readback rechecks the exact active version plus live settings, between equal deployment reads. Remote reads require exactly the expected APP_ORIGIN, three own-Worker DO namespace/class bindings the two secret binding names and CF_VERSION_METADATA. Unexpected or duplicate bindings fail closed. Nonsecret inventory references distinguish secret provisioning records; they cannot prove distinct secret values, which must be established by the separately reviewed isolation/secret-delivery evidence. Secrets never enter a config or manifest.

Required protected repository variables (JSON text, not credentials):

| Variable | Required contents |
| --- | --- |
| `BREWS_DEPLOYMENT_INVENTORY` | Exactly `staging` and `production`; each contains `name` (`brews-bingo-api-staging` / `brews-bingo-api-production`), `account_id` (32 lowercase hex), `origin` (canonical HTTPS DNS origin, no path/port/query/userinfo), `namespace_ids` (ACCOUNTS/GAME_DIRECTORY/GAMES, globally distinct 32-hex IDs), `rate_secret_ref` and `dev_secret_ref` (distinct provisioning references prefixed `staging/` or `production/`). |
| `BREWS_STAGING_ORIGIN` | Exactly the staging inventory origin; checked before the game harness. |
| `BREWS_REVIEWED_READINESS` | Exact schema below; supplied after separate review of actual evidence and the frozen manifest digest, never generated automatically from local tests. |

Both environments require an environment-scoped `CLOUDFLARE_API_TOKEN` authorized only for that environment's reviewed account/Workers scope and safe readback. Staging also requires `BREWS_DEV_CLI_KEY` for the remote harness. Production additionally requires `STAGING_READ_ONLY_CLOUDFLARE_API_TOKEN`: a separately provisioned token restricted to GET/read permissions for the staging Worker/version/settings/deployments, with no upload/deploy or other mutation authority. It is mapped to `CLOUDFLARE_API_TOKEN` only in the dedicated post-approval staging read step; the later production mutation step receives only the separate production token. Missing staging read credentials fail closed. Token scope is separately reviewed external evidence; code cannot establish its provider permissions merely from its name. Production receives no staging management secret, and the harness never runs in production. The production Worker must have its separately provisioned management binding; the workflow does not read or supply that value. No token is passed on a command line, printed, written to a credential file or included in reports. Wrangler output stays captured; temporary config/log paths are private and discarded.

Both jobs use `ENVIRONMENT_READ_TOKEN`, a narrowly scoped GitHub credential with repository **Environments: read**, **Administration: read** (branch protection GET) and **Contents: read** (branch GET), plus access to this repository. A contents-only GITHUB_TOKEN is insufficient. Configure each environment's credential separately. Production must have required independent reviewers, prevent self-review, prohibit admin bypass and restrict deployments to protected branches. `protected_branches: true` alone is insufficient: GitHub can allow every branch when no protection exists.

The tool GET-checks production protection, main branch identity/protected status, and main's effective classic protection. It requires the exact requested main SHA, enforced admins, no force pushes/deletions, at least one approving review, stale-review dismissal, last-push approval, no review bypass actors, and strict required status checks including `validate` bound to an explicit positive app ID. The separately reviewed target setup must ensure that app is GitHub Actions and the check corresponds to the complete validation job. See [GitHub branch protection GET and permissions](https://docs.github.com/en/rest/branches/branch-protection?apiVersion=2022-11-28). These reads occur before staging and immediately before production upload. A ruleset-only configuration whose classic protection GET does not establish these requirements, unavailable plans/permissions, absent checks or malformed/unresolved responses blocks promotion; there is no fallback, inferred protection or bypass. Additional rulesets cannot substitute for the requirements verified here. YAML's `environment: production` does not create required reviewers. Only the protected production job can receive production deployment credentials.

## Reviewed readiness manifest

The JSON object must contain exactly `schema: 1`, `commit`, `manifest_sha256`, `inventory_sha256`, `reviewed_by` (reviewer identity), `expires_at` (future timezone-aware ISO timestamp), `autodeploy_disabled: true`, `runtime_final_01`, `slice_reviews`, and `gates`. The inventory digest is SHA-256 of `deployment.canonical(inventory)`; the manifest digest is emitted by freeze. `runtime_final_01`, `slice_reviews`, and every gate are exact objects with `status: "passed"` and a 64-character `evidence_sha256` binding the separately reviewed actual evidence. Record/source approval is governed by protected-variable write access and independent review; this parser does not independently reproduce external measurements or fabricate their evidence.

`gates` must contain exactly these seven keys, corresponding in order to the seven remaining production checkboxes:

1. `unicode_clock_csprng_sdk`: required deployed normalization, clock, randomness and SDK behavior.
2. `owner_forecast_max_game`: owner forecast and maximum legal game resource/load measurements.
3. `quotas_two_times_headroom`: actual applicable quotas and approved two-times headroom.
4. `history_query_cost`: real History scan/sort/query-plan cost.
5. `copies_retention_restore`: physical copies/backup/log retention and expiry-preserving restore.
6. `isolation_secrets_bootstrap`: actual authorized environments, namespace/secret separation and operator setup.
7. `deployed_security_load_operations`: actual integration/security/load/observability, verification and backout procedures.

The user removed the dedicated `argon2_target` gate on 2026-10-14 and selected the existing library default: Argon2id v19 / 19 MiB / 2 iterations / parallelism 1. No parameter-tuning or dedicated hashing-performance report is required. Update older readiness manifests explicitly: the obsolete eighth key is rejected, while missing or failed remaining gates still block. Normal deployed login/recovery correctness and security tests remain required.

Passing actual RUNTIME-FINAL-01 acceptance under the approved [authorization-time snapshot policy](../plans/protected-response-policy.md) is separately necessary; full Slice 2/6/7 acceptance and the agreed runtime contract belong in `slice_reviews` and `runtime_final_01` evidence. All gates must be reviewed for this exact frozen cut. The local contract requires `status: "passed_authorization_time_snapshot"`, `policy: "authorization_time_snapshot"`, all 20 mandatory actual cases passed, one physical suite, positive exact case inventory, no failures/skips and raw exit 0, with exact policy/suite/original-probe input hashes. Deployment validation reuses the runner’s strict validator. Its separate `superseded_receiving_cut_probe` retains the original physical result: the reproduced older assertion is `failed_acceptance_assertion`, finding RUNTIME-FINAL-01, observed status 200, passed 0 / failed 1 / skipped 0 / raw exit 1 / superseded true. A genuinely passing original observation is also permitted by the strict runner validator; the tool must not require or invent a historical failure. That original denial assertion remains failed under the superseded contract, never relabeled as passed. Its historical failure does not veto the approved acceptance. Missing/new acceptance failure, stale evidence or altered historical classification still blocks. A readiness variable cannot turn failed new acceptance into success. The workflow can remain stopped until current blockers, provider prerequisites and approvals are supplied. Initial deployment and obtaining first actual external evidence require separately authorized operations; ordinary promotion does not bootstrap them. This implementation conservatively requires readiness even before the staging mutation.

## Tools and local verification

Use the full default `release_gate.py --lane all` for promotion evidence. Standalone `--lane worker` intentionally omits the 20 protected snapshot cases; the mandatory `contract` lane runs them exactly once in the all-lane gate, followed by the unchanged old probe as a separate physical historical observation. It does not omit contract acceptance from a full release. Deployment and runner source inventories both bind the same policy/agent/Rust/operations/workflow inputs; an honest complete report cannot be frozen with missing policy hashes.

Run from the workspace root with Python 3.14 for freeze/release (unit tests support 3.11+):

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s backend/tools/tests -p test_deployment.py -v
python3 backend/tools/deployment.py --help
# After a successful full release gate, a clean exact checkout and pinned tools:
python3 backend/tools/deployment.py freeze --commit "$RELEASE_COMMIT" \
  --gate "$RUNNER_TEMP/local-gate/report.json" --output "$RUNNER_TEMP/frozen"
# Use the emitted digest as MANIFEST_SHA256 on every subsequent command:
python3 backend/tools/deployment.py verify --commit "$RELEASE_COMMIT" \
  --manifest-sha256 "$MANIFEST_SHA256" --artifact "$RUNNER_TEMP/frozen"
python3 backend/tools/deployment.py config --environment staging \
  --commit "$RELEASE_COMMIT" --manifest-sha256 "$MANIFEST_SHA256" \
  --artifact "$RUNNER_TEMP/frozen" --output "$RUNNER_TEMP/staging-config.json"
python3 backend/tools/deployment.py deploy --dry-run --environment staging \
  --commit "$RELEASE_COMMIT" --manifest-sha256 "$MANIFEST_SHA256" \
  --artifact "$RUNNER_TEMP/frozen"
```

Output files/directories must be new; freeze output is outside the repository. No command installs or provisions a secret. Additional commands are `pack --archive NEW_FILE`, `unpack --archive FILE --output NEW_DIR`, `readiness`, `protection`, `deploy --environment ... --output NEW_IDENTITY_FILE`, `readback --expected-identity FILE`, and `smoke`. All except unpack/protection/freeze require the exact commit/artifact/manifest digest. Real deploy/readback/protection/smoke issue remote requests and require separate execution authorization; none were run during this implementation. API errors/redirects, insecure TLS, non-JSON responses, partial traffic splits and ambiguous identities block. There is no disabled-check or bypass option.

`staging-test` invokes the actual `backend/tests/full_game_e2e.py` with `--origin`, `--expected-origin`, `--environment staging`, `--output NEW_PRIVATE_DIR`, `--bootstrap-cli FROZEN_PATH`, and staging-only `BREWS_DEV_CLI_KEY`/`BREWS_API_ORIGIN`. The origin must equal the canonical inventory origin; loopback/local evidence is rejected. The producer captures all child stdout/stderr and never prints the harness summary or raw failures. It requires actual process exit 0 and exact agreement between process output and the fresh `summary.json`: passed staging game, `own_account_removed`, retained contractual History, exactly three players, five or six accepted calls, at least five snapshot ACKs, and sorted unique checks with an exact count. It derives the complete check inventory from label expressions in the original frozen harness source, accounting for four/five manual calls, all player checks, actual cleanup-absence check and optional spectator terminal delivery. Unsupported source/check shapes block. This parses actual observations; it does not generate gameplay evidence. Proof helpers do not approve readiness.

Before the game and after cleanup immediately before proof creation, provider GET readback requires the same exact active deployment/version, commit/code annotations, namespaces and origin. Both reads also GET `/api/deployment` anonymously and require its serving version ID to equal the provider version. Freeze verification rechecks the exact source/manifest/assets and original archive before/after the game. This binds host routing and test execution to the tested Worker. The source must be separately reviewed and the endpoint provisioned through separately authorized setup.

The only staging evidence transferred is `staging-proof-${{ github.run_id }}` via immutable upload-artifact, with its SHA-256 in the staging job's trusted output. Its exact schema is `schema: 1`, decimal `run_id`, `commit`, `manifest_sha256`, `archive_sha256`, `inventory_sha256`, `staging_identity` (`deployment_id`, `version_id`, `worker`, `commit`, `code_sha256`), `summary_sha256` and the strictly allowlisted `summary`. Summary SHA-256 covers canonical summary JSON. No boards, account/player/game IDs, cookies, credentials or raw diagnostics are included. Production downloads only this same run's proof and verifies its trusted output digest, run/commit/manifest/archive/inventory cut, source hashes, identity and successful summary. Production environment variable overrides that change either inventory fail. The protected production job then rechecks the exact tested staging identity **after human approval and before any production mutation**, using only the staging read-only token. The later deploy step validates the same proof again under production credentials. Drift requires a new staging execution. The provenance boundary is trusted same-run workflow outputs plus immutable artifacts, not a standalone cryptographic signature. These checks do not provision targets or close the eight external gates.

Command shapes (same exact frozen commit/manifest/artifact required):

```sh
python3 backend/tools/deployment.py staging-test --commit "$RELEASE_COMMIT" \
  --manifest-sha256 "$MANIFEST_SHA256" --artifact "$RUNNER_TEMP/frozen" \
  --archive "$RUNNER_TEMP/transfer/release.zip" --archive-sha256 "$ARCHIVE_SHA256" \
  --run-id "$GITHUB_RUN_ID" --expected-identity "$RUNNER_TEMP/staging-identity.json" \
  --output "$RUNNER_TEMP/staging-proof.json"
# After production approval, staging READ-ONLY credential scoped to this step:
python3 backend/tools/deployment.py verify-staging --commit "$RELEASE_COMMIT" \
  --manifest-sha256 "$MANIFEST_SHA256" --artifact "$RUNNER_TEMP/frozen" \
  --archive-sha256 "$ARCHIVE_SHA256" --run-id "$GITHUB_RUN_ID" \
  --proof "$RUNNER_TEMP/staging-evidence/staging-proof.json" --proof-sha256 "$PROOF_SHA256"
# Later step with separate production credentials; ordinary readiness still mandatory:
python3 backend/tools/deployment.py deploy --environment production --commit "$RELEASE_COMMIT" \
  --manifest-sha256 "$MANIFEST_SHA256" --artifact "$RUNNER_TEMP/frozen" \
  --archive-sha256 "$ARCHIVE_SHA256" --run-id "$GITHUB_RUN_ID" \
  --proof "$RUNNER_TEMP/staging-evidence/staging-proof.json" --proof-sha256 "$PROOF_SHA256" \
  --output "$RUNNER_TEMP/production-identity.json"
```

Production runs only a nonmutating GET to an unknown route expecting 404, followed by exact production identity readback. This smoke is deliberately limited and does not certify gameplay or capacity. These remote commands were not executed locally; local proof tests use clearly synthetic fixtures that are never evidence of an actual staging game.

## Migrations and backout

There are no new SQL or DO migrations in this slice. Preserve the existing in-Object SQL migration behavior and historical tags; do not reset storage or restore a copy as routine backout. Review both old/new binary schema readability and alarm/outbox/receipt compatibility, including partially applied per-Object SQL upgrades, before any separately authorized version backout. Use the existing [expiry-preserving restore/backout worksheet](restore-and-backout.md); forward-fix or quarantine when partial-version/schema compatibility is unproven. These are prerequisites, not a tested provider rollback claim.

Public documentation was read; authenticated provider APIs were not queried. Actual responses still require target verification and fail closed if their shape differs.
